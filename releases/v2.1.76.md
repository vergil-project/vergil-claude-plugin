# Release 2.1.76 (2026-11-18)

## Bug fixes

- **wait on vrg-pr-await in the background so a long CI run is not cut off (#1148)**
  Since vrg-pr-await waits until the PR merges (up to $VRG_FINALIZE_DEADLINE, 7200s by default), the old foreground-only rule let Claude Code's 600s foreground cap kill the wait. pr-watch now runs it as a background command where the harness notifies on exit, and otherwise as short foreground waits under the harness timeout that loop on timed_out up to the full deadline. One wait per pass, never polled. Ref #1147

## Documentation

- **describe submit-time auto-merge in skills and the agent-merge hook (#1145)**
  * docs(skills): describe submit-time auto-merge in skills and the agent-merge hook

  fixture-run, epic-implement and issue-implement now say the human's vrg-submit-pr opens PRs with auto-merge on (squash for one issue, rebase for a batch) and finalizes by default, and that vrg-finalize-pr watches and settles but never merges. The block-agent-merge deny message, its README row and its hooks reference page say merging is a human action through submit's auto-merge; the hook's behaviour is unchanged. Ref #1123.

  * fix(hooks): quote the agent-merge deny reason for shellcheck

  Builds the reason in double quotes with escaped backticks, so shellcheck's SC2016 no longer flags it. Ref #1123.

## Features

- **watch PRs that auto-merge (#1143)**
  * feat(pr-watch): watch PRs that auto-merge

  * fix(pr-watch): fold a batch PR's fixups onto its own base so a fold never rebases

- **warn when a vergil skill is served from a stale plugin version (#1144)**
  * feat(hooks): warn when a vergil skill is served from a stale plugin version

  A running session keeps serving the plugin version it loaded at start, even after a newer one is installed. A new PreToolUse hook on the Skill tool compares the loaded plugin folder with the install path in installed_plugins.json before each vergil: skill call and, on a mismatch, adds a warning to the agent's context naming both versions and asking it to have the human run /reload-plugins or restart. It never blocks; a check that cannot run is reported, never treated as a match. The README now says /reload-plugins after the install commands is a valid alternative to a restart.
