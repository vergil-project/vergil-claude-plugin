    Hooks¶

    The plugin provides PreToolUse and PostToolUse hooks that enforce workflow guardrails mechanically, and one SubagentStop hook that stores the merge reviewer's reply. These replace duplicated documentation rules across all consuming repos — rules that humans and agents alike routinely drift from when enforcement is prose-only.

    Looking for the overall workflow? See vergil-tooling → Git Workflow for the big-picture guide covering branching, commit/PR/finalize cycle, and worktrees. This page is the reference for the plugin's hooks specifically; where each validation check runs is covered in vergil-tooling → Validation Matrix, and the per-repo hook guard in vergil-tooling → Hook Guard.

    Each entry below covers what the hook catches, why it exists, and how to achieve the intent correctly when the hook blocks you.

    Reading issue and PR content is guarded by vergil-tooling, not by a hook of this plugin: since vergil-tooling v2.1.338, its hook guard refuses an agent's raw issue and PR content reads (a body or comment read, or a list or search that matches text or asks for a content field) and names vrg-issue-read, which prints only what a trusted identity wrote and reports the rest as metadata.

    Managed-repo gating¶

    Every hook below except block-heredoc and warn-stale-plugin-version is gated on a managed-repo check. A repo is "managed" when vergil.toml exists at the repo root.

    When the marker is not present, the gated hooks short-circuit to a no-op so the plugin doesn't interfere with ad-hoc git work in unrelated repositories. block-worktree-bypass-write has exceptions that apply everywhere: it denies a relative target path; without python3 it denies every Write and Edit; and it denies a write whose path python3 cannot normalise. Detection is a pure-shell walk up from the bash session's CWD looking for the marker, terminating at a .git boundary or the filesystem root. No git subprocess; the gate's overhead is a handful of stat() calls.

    The SubagentStop hook capture-merge-review-result is not gated either: it acts only on a vergil:merge-reviewer stop whose request file lies in a task's private directory, which is itself in a managed repo.

    block-heredoc is intentionally not gated — heredoc syntax in CLI invocations breaks unpredictably regardless of which repo you're in, so the rule is universal.

    See issue #87 for the rationale.

    Command matching: quote-stripping¶

    Every Bash-command matcher below (except block-heredoc) tests tool names against a quote-stripped copy of the command string: single- and double-quoted spans are replaced with "" first, then the tool name must appear in command position ((^|[;&|({]\s*)<tool>(\s|$), applied per line).

    This is why a commit body or issue body that mentions a blocked command — even at the start of a line inside a multi-line --body argument — does not trigger a false deny, while the same text in command position still does.

    block-heredoc matches raw text: its regex must see the quoted delimiter in <<'EOF', which stripping would remove.

    Canonical rule, accepted gaps, and the shared test vectors: docs/specs/2026-06-05-450-command-matcher-quoting-design.md. See issue #450.

    Malformed input fails closed¶

    Every PreToolUse hook below except warn-stale-plugin-version, which warns and never blocks, refuses a tool call it cannot check rather than letting it through. That covers empty stdin, input that is not valid JSON or is not a single JSON object, a missing jq, and a payload without the hook's required field (tool_input.command for the Bash hooks, tool_input.file_path for block-worktree-bypass-write, tool_input.file_path or tool_input.notebook_path for guard-merge-review-results). The hook exits with code 2, the PreToolUse blocking exit code, so Claude Code refuses the call and shows the agent a stderr message naming the problem:

    block-agent-merge.sh: blocked: the hook input is not valid JSON. This hook cannot check the tool call, so it fails closed and refuses it. This is a hook-protocol problem, not a problem with the command itself.

    Behaviour on well-formed input is unchanged, including an empty command string, which is allowed. Scope matches the managed-repo gating: a gated hook still allows everything outside a managed repo. Unparseable input names no usable cwd, so the gate then checks the hook process's own working directory. block-heredoc is not gated, so it refuses unparseable input everywhere. guard-audit-writes refuses it everywhere for the audit identity and still ignores other identities; its missing-path case keeps its JSON deny. The shared reader is hooks/scripts/lib/hook-input.sh; tests are in hooks/tests/hook-input.test.sh. vrg-hook-guard and the per-repo guard.sh shim follow the same rule (vergil-tooling#3773). See issue #776.

    The PostToolUse hook detect-deprecation-warnings is advisory and is not changed: a PostToolUse hook runs after the tool call, so it has nothing to refuse. The SubagentStop hook capture-merge-review-result has no call to refuse either: on any problem it stores nothing and exits 1 (see its entry).

    PreToolUse Hooks — Bash¶

    block-raw-git-commit¶

    What. Denies Bash tool invocations that call git commit (or pipe-chained equivalents).

    Why. vrg-commit constructs standards-compliant conventional commit messages. Hand-written git commit -m invocations drift from the commit-message standard over time. Commits carry no AI co-author trailer; Claude Code attribution is turned off in .claude/settings.json (vergil-project/vergil-tooling#3200).

    Alternative. Use vrg-commit with the appropriate --type, --scope, --message, and --body flags.

    block-raw-gh-pr-create¶

    What. Denies Bash tool invocations that call gh pr create.

    Why. vrg-submit-pr builds standards-compliant PR bodies with proper issue linkage keywords (Fixes, Closes, Resolves, Ref) that the pr-issue-linkage CI validator requires. Manual gh pr create commands routinely ship without linkage and fail CI on the first try.

    Alternative. Use vrg-submit-pr with --issue, --summary, --linkage, and --notes flags.

    block-protected-branch-work¶

    What. Denies Bash tool invocations that run raw git commit when the effective working directory falls outside the worktree convention's allowed locations. It does not match vrg-commit.

    Why. Behavior depends on whether the target repo has adopted the worktree convention. The hook detects adoption by looking for a .worktrees/ line in the repo's .gitignore. On adopted repos, commits must originate from inside .worktrees/<name>/; the main tree is read-only for source (ignored scratch in its build/ is not a source edit). On non-adopted repos, the hook falls back to the legacy behavior of blocking commits on main or develop regardless of directory.

    Alternative. On adopted repos: create a worktree with git worktree add .worktrees/issue-N-<slug> -b feature/N-<slug> origin/develop and run all edits + commits from inside that directory. On non-adopted repos: create and check out a feature branch with a name matching the repo's branching_model prefixes.

    This hook complements vrg-commit's own protected-branch check — that check runs inside vrg-commit against the branch of the directory it actually executes in, so it is the authoritative guard for vrg-commit. This hook only guesses the target repo from the session cwd and the command text, and under the sandbox that cwd is reset to the project root, so matching vrg-commit here produced false denies for worktree commits in sibling repos (#694). The hook therefore covers raw git commit only.

    block-heredoc¶

    What. Denies Bash tool invocations that contain heredoc syntax (<<EOF, <<'EOF', etc.) in CLI arguments.

    Why. Heredocs routinely produce incorrect escaping when passed through multiple shell layers (agent → Bash tool → subprocess → CLI). Several CLIs (gh, git commit, curl) silently succeed with malformed content, producing invalid commit messages, broken PR bodies, or corrupt JSON bodies. Writing to a file and passing it via --body-file / --file / $(cat <path>) avoids the entire class of bug.

    Alternative. Write the multi-line content to a temp file and reference it: --body-file /tmp/body.txt or --body "$(cat /tmp/body.txt)".

    block-associative-arrays¶

    What. Denies Bash tool invocations that use bash 4+ associative arrays (declare -A, typeset -A).

    Why. The hook scripts and vrg-container-run dispatcher themselves run on the host shell, which on macOS is bash 3.2 (Apple has not shipped a newer bash since the GPL license change). Associative arrays silently fail on macOS bash 3.2, producing hard-to-debug behavior. Inside the dev container bash is modern, but the scripts that launch the container cannot assume that environment.

    Alternative. Use parallel indexed arrays, or switch to awk/jq for key-value lookups. If you genuinely need associative arrays, the code belongs inside the container, not in host scripts.

    enforce-host-container-split¶

    What. Warns (via additionalContext, never a deny) when a container-only language-toolchain command is invoked bare on the host, at the start of a command or after a separator (e.g., ruff check .), per the host-vs-container split from #96. The warning names the wrapped form for an ad hoc run and reminds the agent that a full vrg-container-run -- vrg-validate is still required before handoff:

    WARNING: ruff runs in the dev container: use vrg-container-run -- ruff … for an ad hoc run; a full vrg-container-run -- vrg-validate is still required before handoff.

    The wrapped form, vrg-container-run -- <tool> …, passes silently. So does a host-only tool wrapped in vrg-container-run -- (e.g., vrg-container-run -- gh issue list): the hook no longer checks it. A host tool run in the container fails on its own (it needs the SSH agent, the host git config or host gh auth), and the full vrg-validate before handoff is the backstop.

    The container-only tool list lives in hooks/scripts/lib/host-container-tools.sh.

    Why. Container-only tools are not installed on the host, so a bare call fails or, worse, runs a different host version than the one validation uses. An ad hoc wrapped run of one linter is a legitimate way to iterate (#993); the full vrg-validate run remains the only gate that counts before handoff.

    Alternative. Wrap the tool: vrg-container-run -- <tool> … for an ad hoc run, and vrg-container-run -- vrg-validate before handoff.

    block-autoclose-linkage¶

    What. Denies vrg-submit-pr invocations that pass --linkage Fixes, --linkage Closes, or --linkage Resolves.

    Why. These keywords auto-close the linked issue when the PR merges. Under the 2.1 workflow issues are closed explicitly by the human after PR finalization (vrg-finalize-pr) — an issue closed automatically at merge time signals "done" before the human has confirmed the work cycle is complete. Closing is deliberately manual today; agents have closed issues incorrectly, so no automation owns it (a future close-analysis agent may).

    Alternative. Use --linkage Ref. Issue closing is the human's post-finalization action — not the agent's.

    block-agent-merge¶

    What. Denies Bash tool invocations that call gh pr merge, gh pr review --approve, or the equivalent gh api calls — unconditionally.

    Why. No agent merges a PR directly or approves one: a PR merges only through vrg-submit-pr, which opens it with auto-merge on, and vrg-finalize-pr only watches and settles. Skill prose saying "do not merge" is advisory; agents rationalize past it. This hook makes the rule mechanical — an ergonomic fast-fail on top of the hard credential and server-side gates. The deny applies to all identities and all branches, release PRs included; the pre-2.1 release-branch allow-list (delegated to a vrg-check-pr-merge tool that was never shipped) was removed in #441. See #162 for the original motivating incident.

    Alternative. Open the PR with vrg-submit-pr. It turns auto-merge on, so the PR merges by itself once its checks pass.

    block-github-contents-api¶

    What. Denies gh api calls that write (PUT/POST/DELETE) to the GitHub Contents API. Reads (GET) are allowed.

    Why. Writing files via the API bypasses the local workflow entirely — no validation, no commit standards, no PR template. File changes go through the worktree: edit, vrg-commit, hand off with vrg-pr-workflow report-ready, and open the PR with the agent's own vrg-submit-pr. (vrg-gh denies gh api outright; this hook catches raw gh.)

    Alternative. Make the change in your worktree and follow the local workflow.

    PreToolUse Hooks — Write|Edit¶

    block-worktree-bypass-write¶

    What. Blocks Write/Edit file modifications targeting the main worktree when the parallel-AI-agent worktree convention is active.

    Why. The main worktree is read-only for source by convention — all edits flow through a .worktrees/<name>/ worktree on a feature branch. The convention's build/ exception allows ignored scratch in the main clone's build/ (the MQ lab's shared live-lab state lives there), and build/.vergil-state/ is the namespace for agent state (the paad review doctrine's state directories). Of the main worktree, the hook allows Write and Edit only under build/, the one place the human can see what agents write, and there only to paths git reports as ignored. Every target path is normalised first (., .. and symlinks resolved, for new files as well as existing ones) with python3, and matched where it leads: a path that leads out of build/ through .. or a symlink, or through a build that is itself a symlink, is not allowed as build/ scratch. A relative target path is denied. Without python3 the hook denies every Write and Edit, wherever it points; a write whose path python3 cannot normalise is denied. Design: docs/specs/2026-05-09-worktree-write-guard-design.md. Tests: hooks/tests/block-worktree-bypass-write.test.sh.

    Alternative. Write to your assigned worktree's absolute path.

    guard-audit-writes¶

    What. When VRG_IDENTITY_MODE=audit, denies Write/Edit/ NotebookEdit calls targeting anything other than .vergil/audit-* (the audit's own artifacts) or build/ (scratch space) inside the worktree. Other identities are never constrained by this hook. The target path is fully resolved with os.path.realpath before the match, for a new file as well as an existing one.

    Why. The 2.1 workflow spec makes the AUDIT identity "read-only by discipline, not by sandbox" — this hook turns the discipline into a mechanical gate per the no-honor-system principle. The allowlist deliberately excludes .vergil/pr-workflow.json: that file is the USER agent's PR workflow state, written by vrg-pr-workflow report-ready, and the input of the agent's own vrg-submit-pr.

    Soft gate, by design. Identity comes from an environment variable a misbehaving agent can unset; every in-VM guard is soft. It steers a correctly behaving agent — hard enforcement lives at the per-identity GitHub App credentials, the pinned vergil-audit/approved required check, and the VM sandbox. Keeping the guard simple is the accepted trade-off. Bash-command writes (>, tee, sed -i …) are a documented gap for the same reason.

    Failure mode. Fail-closed inside the audit identity (no path, unresolvable path, or path escaping the worktree → deny; input that cannot be parsed → blocked with exit 2); fail-open outside it.

    Alternative. Write audit findings to .vergil/audit-feedback.yml; use build/ for scratch. Tests: hooks/tests/guard-audit-writes.test.sh.

    guard-merge-review-results¶

    What. Denies Write, Edit and NotebookEdit on a stored merge-review result, result-<step>.md, its publishable copy, reply-<step>.md, or its capture record, capture-<step>.json, in any task's private directory (build/.vergil-state/issue-implement/<N>/merge-review/), for every identity. The path is matched as given and, with python3, with every symlink resolved.

    Why. The review record must be kept exactly as the reviewer returned it. Only capture-merge-review-result writes these files; an agent that retypes a result can shorten its prose while keeping its result block, which vrg-merge-review-check cannot see (#1065).

    Soft gate. Bash-command writes are not matched. The capture record's SHA-256 is what lets a check catch an edit made any other way.

    Alternative. Read the result. For a new one, rebuild the step's request and dispatch the reviewer again, as the merge-review skill says. Tests: hooks/tests/guard-merge-review-results.test.sh.

    PreToolUse Hooks — Skill¶

    warn-stale-plugin-version¶

    What. Before each Skill call for a vergil: skill, compares the plugin folder the session loaded (CLAUDE_PLUGIN_ROOT, a version directory under ~/.claude/plugins/cache/<marketplace>/vergil/) with the installPath that ~/.claude/plugins/installed_plugins.json records for vergil@<marketplace>. The install that applies is the local-scope, then the project-scope entry whose projectPath is the session's project (CLAUDE_PROJECT_DIR, else the payload's cwd), else the user-scope entry. Paths are compared with symlinks resolved. On a mismatch it adds a warning to the agent's context naming the loaded and the installed version. It tells the agent to note the warning and carry on, not to stop, and to tell the human, who can run /reload-plugins (or restart the session) when the work depends on the new version. A check that could not run ends the same way. CLAUDE_CONFIG_DIR, when set, replaces ~/.claude.

    Why. A running session keeps serving the plugin version it loaded at start, even after a newer one is installed. An agent that trusts the loaded skill after an upgrade can silently do what the release removed (#1129). Claude Code tells the human "Plugins changed. Run /reload-plugins to activate.", but that notice never reaches the agent, and an agent cannot run a slash command itself. The warning does not stop the agent: most plugin updates land mid-task and do not touch the work in progress, so stopping on every one interrupts for nothing. When the work does depend on the new version, the human pauses the session and reloads (#1260).

    Warns, never blocks. The hook only adds context: it never denies the call, so a session that cannot reload (a remote one, say) is not trapped. It is not gated on a managed repo, and it is the one PreToolUse hook that does not fail closed: every problem that stops the check (unparseable or empty input, an unset CLAUDE_PLUGIN_ROOT, a missing or unreadable installed_plugins.json, no install record for the session, an entry with no installPath) is reported in the added context as a check that could not run, never treated as a match. Without jq it can build no response, so it prints the problem to stderr and exits 1, a non-blocking error. A plugin root outside the plugin cache, such as a claude --plugin-dir source mount, has no install record to compare with, so the hook is silent there.

    Alternative. When the work depends on the new version, the human runs /reload-plugins in the session, or restarts it, and the agent then invokes the skill again. Tests: hooks/tests/warn-stale-plugin-version.test.sh.

    PostToolUse Hooks — Bash¶

    detect-deprecation-warnings¶

    What. Scans test output and command output for deprecation warnings; surfaces them to the agent for triage.

    Why. Deprecation warnings get silently tolerated for months until the deprecated feature is removed. Surfacing them at the moment they first appear makes them trackable via the deprecation-triage skill while the context is fresh.

    Alternative. Triage the warning via the deprecation-triage skill — either fix it now or capture it in a tracking issue with clear resolution criteria.

    SubagentStop Hooks — vergil:merge-reviewer¶

    capture-merge-review-result¶

    What. When a vergil:merge-reviewer subagent stops, stores its last message (last_assistant_message in the hook input), byte for byte, as result-<step>.md next to the request it answered, and writes capture-<step>.json beside it. The hook input carries the reviewer's own text, unlike the subagent's completion notice, which escapes &, < and > as HTML entities, so the stored result is never escaped or decoded:

    {"schema": "merge-review-capture/1", "step": "review",
 "request_id": "<the request's request_id>",
 "result_sha256": "<SHA-256 of result-review.md>",
 "agent_id": "<the reviewer subagent's ID>"}

    The reviewer's whole prompt is the absolute path of its request file, so the hook reads that path from the first user message of the reviewer's transcript (agent_transcript_path). It writes only when the path is a request-<step>.json in a task's private directory, the request's step matches its name, and vrg-merge-review-request --ensure-dir, run for the request's issue from its worktree, prints that same directory.

    It also writes reply-<step>.md, the publishable copy of the same bytes: the reply inside a fenced block whose backtick fence is longer than any backtick run in the reply, in a collapsed <details> section whose summary gives the reply's SHA-256 and size. A reply that does not end in a newline gets one before the closing fence, and the summary says so. The skill appends this copy unread to the step's public comment when no security finding is in the result or, for a check, in an earlier step, and the skill's screen of the result withheld nothing, so the full reply survives the private directory's deletion at report-ready.

    All three files are written mode 600 and moved into place, the capture record last.

    Why. The merge-review skill used to copy the reply out of the subagent's output itself. A retyped reply could lose prose while keeping its result block, and vrg-merge-review-check checks only the block (#1065). The reviewer keeps its read-only tools (Read, Glob, Grep); the hook does the writing.

    Failure mode. Any other subagent type is a no-op. On any problem the hook stores nothing, prints the reason on stderr and exits 1, a non-blocking error: exit 2 would keep the reviewer running and change its last message. The skill deletes the step's result before each dispatch and confirms the capture after it, so a failed capture ends the run with error rather than going unseen.

    Tests: hooks/tests/capture-merge-review-result.test.sh.

    Hooks module (mod)¶

    Besides its settings hooks, hooks/hooks.json names one hooks module under modules: hooks/register.tsx, a Claude Code mod that runs inside Claude Code rather than as a script. It holds one hook.

    Agent row labels¶

    A ui.render hook on the AgentRow render site, a subagent's or teammate's row in the agent panel. When several subagents run in parallel (an epic-implement run, say), Claude Code shows each row as its agent type, general-purpose, and its latest activity, so the rows cannot be told apart. The hook redraws a row as the task and issue(s) the agent was dispatched for, how long it has been running (or done, failed or stopped once it has ended), and the first line of its latest activity:

    Task 15 (vergil-tooling#4931) · 4m12s · Running the test suite
Batch 6b/6c/9/10 (#4917, #4918, #4926, #4927) · done

    The label comes from the Agent call's description. Every issue reference in it (owner/repo#N, repo#N or #N) is listed once, in order, with the owner dropped; a Task <id> or Batch <id>/<id>… in it leads the label. A description that names no issue (an Explore fan-out, say), a row the person's settings hide, and a row they already redraw (its body arrives set) are left as Claude Code draws them.

    AgentRow needs Claude Code v2.1.326 or later. An older version loads the module but never raises the site, so rows stay as they were; claude plugin validate there warns that no component is named AgentRow. Mods are on by default; disableAllHooks stops this one along with the settings hooks.

    Tests: hooks/tests/register.test.tsx, run with claude plugin test . from the repo root on Claude Code v2.1.326 or later. vrg-validate does not run them, since its container has no Claude Code.

    Hooks deliberately not provided¶

    Per-edit linting / validation¶

    The plugin does not ship a PostToolUse Write|Edit hook that runs ruff / mypy / yamllint / markdownlint / shellcheck on each edited file. An earlier version did (validate-on-edit.sh plus per-language validate-*.sh scripts); it was removed in #91.

    Why removed. Each per-edit invocation paid the dev-container startup cost (1–3 s on typical hardware) for one file's worth of work — five container starts for a single Python edit (ruff check --fix, ruff format, ruff check, mypy, ty check). Across a session with dozens of edits, that's minutes of wall-clock overhead per session, every session. The same checks already run in two cheaper places: vrg-validate covers them in a single container start before PR submission, and CI re-runs them on every PR. The per-edit layer was the third copy with the worst cost-per-value ratio.

    What replaces it. Nothing per-edit. Validation runs at PR time via vrg-validate, which is the documented "only validation command" per every consuming repo's CLAUDE.md. The block-raw-git-commit PreToolUse hook already enforces commits going through vrg-commit, which checks the branch and worktree context before committing: it refuses a detached HEAD, a protected branch, a branch name that does not match the branching model or lacks an issue number, and a feature-branch commit from the main worktree. vrg-commit does not run validation itself; that happens in vrg-validate and again in PR CI.

    Don't re-add this. A future contributor noticing the absence should resist the impulse to re-add per-edit validation as a "missing feature." The cost-per-value math doesn't work; the gap is intentional.

    Stop hook for finalization¶

    The plugin no longer ships a Stop hook that blocks session exit on "PR submitted but vrg-finalize-repo not run." That hook (stop-guard-finalization.sh) was removed in #56.

    Why removed. The agent records its PR with vrg-pr-workflow report-ready, which writes .vergil/pr-workflow.json, then runs vrg-submit-pr itself, which opens the PR with auto-merge on and always finalizes: it blocks while vrg-finalize-pr watches the PR to a merge or to a reason it cannot merge. No state is left where a PR is submitted but not finalized, so a session-end gate keyed to it has no correct trigger.

    What replaces it. Nothing needs to: finalization is part of the submit. When a PR does not merge, pr-watch fixes it and reruns vrg-finalize-pr itself after each fix. The retired remind-finalize PostToolUse hook (removed in #441) is gone for the same reason: a reminder to finalize after vrg-submit-pr has nothing left to remind.

    Don't re-add this. Re-adding a session-end finalize gate would block the standard PR submission workflow and force agents into broken cleanup behavior just to satisfy the hook.

    How hooks work — technical¶

    Hooks are defined in hooks/hooks.json and implemented as shell scripts in hooks/scripts/. Each hook receives the tool input as JSON on stdin and returns a JSON response indicating whether to allow, deny, or annotate the action.

    Every script that hooks.json names must be tracked in git at mode 100755 (executable): Claude Code cannot run a hook script that is not. The repo's custom validator, scripts/bin/validate-custom (check_hook_modes), fails the vrg-validate pipeline when one is untracked or has any other mode. Each hooks.json command must start with ${CLAUDE_PLUGIN_ROOT}/ so the check can find its script.

    PreToolUse response¶

    A PreToolUse hook can deny an action by writing JSON to stdout and exiting 0:

    {
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Reason the action is being denied."
  }
}

    Exit 0 with no JSON = allow. Exit 2 = block: Claude Code refuses the call and feeds stderr to the agent. The plugin uses exit 2 for input it cannot parse (see Malformed input fails closed). Any other non-zero exit is a non-blocking error, and the call goes ahead.

    A PreToolUse hook can also add context for the agent without a decision, and the call then goes ahead as usual (warn-stale-plugin-version does this):

    {
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "additionalContext": "Message surfaced to the agent."
  }
}

    PostToolUse response¶

    A PostToolUse hook can inject context by writing JSON and exiting 0:

    {
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "Message surfaced to the agent."
  }
}

    PostToolUse hooks cannot un-do the tool action; they can only add context the agent sees in its next turn. Exit 2 is a fatal hook error — useful when validation cannot run and the absence of validation should be visible.

    Stop response¶

    A Stop hook can block session exit by returning:

    {
  "decision": "block",
  "reason": "Reason the session cannot exit."
}
